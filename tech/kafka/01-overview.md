# 카프카 개요 — 메시지 큐와 카프카를 쓰는 이유

## 개념

### 메시지 큐 (Message Queue)
서비스끼리 **직접 호출하지 않고, 중간 저장소에 메시지를 넣고 꺼내 가는 방식**으로 통신하는 구조.

- **Producer**: 메시지를 보내는 쪽
- **Consumer**: 메시지를 받아서 처리하는 쪽
- **Broker**: 중간에서 메시지를 보관하고 전달하는 서버

```
[주문 서비스] --메시지--> [Broker] --메시지--> [결제 서비스]
                                   \--메시지--> [알림 서비스]
```

이렇게 하면 보내는 쪽은 받는 쪽이 누구인지, 지금 살아 있는지 몰라도 된다 → **비동기 + 느슨한 결합(decoupling)**.

### 카프카 (Apache Kafka)
LinkedIn에서 대용량 로그/이벤트를 처리하려고 만든 **분산 이벤트 스트리밍 플랫폼**.
일반적인 메시지 큐처럼 쓸 수 있지만, 본질은 **"디스크에 순서대로 쌓이는 로그(append-only log)"** 에 가깝다.

| 용어 | 의미 |
|---|---|
| Topic | 메시지를 분류하는 이름 (예: `order-created`) |
| Partition | 토픽을 나눈 단위. 병렬 처리와 순서 보장의 기준 |
| Offset | 파티션 안에서 메시지의 순번 |
| Consumer Group | 같은 토픽을 나눠서 처리하는 컨슈머들의 묶음 |

> 자세한 구조는 [02-architecture.md](02-architecture.md)에서 정리.

## 동작 원리

1. **Producer가 토픽에 메시지를 보낸다.**
   키(key)가 있으면 키의 해시로 파티션이 정해지고, 없으면 여러 파티션에 분산된다.
2. **Broker는 메시지를 파티션 끝에 이어 붙여(append) 디스크에 저장한다.**
   각 메시지는 파티션 내에서 증가하는 offset을 받는다.
3. **Consumer가 원하는 offset부터 읽어 간다 (Pull 방식).**
   브로커가 밀어주는(push) 게 아니라 컨슈머가 자기 속도에 맞춰 가져간다.
4. **Consumer는 어디까지 읽었는지 offset을 커밋한다.**
   장애 후 재시작하면 커밋된 offset부터 다시 읽는다.
5. **메시지는 읽어도 삭제되지 않는다.**
   보관 기간(retention, 기본 7일)이나 용량 기준으로만 삭제된다.
   → 여러 컨슈머 그룹이 같은 데이터를 각자 읽을 수 있고, 과거 데이터를 **다시 읽는(replay)** 것도 가능하다.

### 전통적인 메시지 큐(RabbitMQ 등)와의 차이

| | 전통적인 MQ (RabbitMQ) | Kafka |
|---|---|---|
| 전달 방식 | Broker가 Push | Consumer가 Pull |
| 메시지 보관 | 소비되면 삭제 | 보관 기간 동안 유지 |
| 재처리 | 어려움 | offset을 되돌려 replay 가능 |
| 순서 보장 | 큐 단위 | 파티션 단위 |
| 강점 | 복잡한 라우팅, 개별 메시지 처리 | 대용량 처리량, 스트리밍 |

### 카프카가 빠른 이유
- **순차 디스크 I/O**: 랜덤 접근 없이 파일 끝에만 쓰기 때문에 디스크여도 빠르다.
- **OS 페이지 캐시 활용**: 자체 캐시 대신 OS 캐시를 사용.
- **Zero-copy**: 디스크 → 네트워크로 보낼 때 유저 공간 복사 없이 커널에서 바로 전송(`sendfile`).
- **배치 + 압축**: 메시지를 묶어서 보내고 저장.
- **파티션 단위 병렬 처리**: 파티션 수만큼 컨슈머를 늘려 수평 확장.

## 장단점 / 비교

### 장점
- **높은 처리량**: 초당 수십만~수백만 건 처리 가능.
- **수평 확장**: 브로커와 파티션을 추가해 확장.
- **내구성/고가용성**: 디스크 저장 + 브로커 간 복제로 장애에도 데이터 유지 ([05-replication.md](05-replication.md)).
- **재처리 가능**: 메시지가 남아 있어 버그 수정 후 다시 처리하거나 새 서비스가 과거 데이터부터 읽을 수 있다.
- **다수 컨슈머**: 하나의 이벤트를 여러 서비스가 독립적으로 소비.
- **느슨한 결합**: Producer와 Consumer가 서로를 몰라도 된다.

### 단점
- **운영 복잡도**: 클러스터 구성, 파티션 수 설계, 모니터링 등 관리 부담이 크다.
- **순서는 파티션 안에서만 보장**: 토픽 전체 순서가 필요하면 파티션을 1개로 해야 해서 확장성을 잃는다.
- **개별 메시지 처리 기능이 약함**: 메시지별 ACK, 우선순위 큐, 지연 메시지, 복잡한 라우팅은 RabbitMQ가 더 적합.
- **소규모엔 과함**: 트래픽이 적은 서비스라면 오버엔지니어링이 될 수 있다.
- **중복 처리 가능성**: 기본은 at-least-once라 컨슈머가 멱등하게 처리해야 한다 ([06-delivery.md](06-delivery.md)).
