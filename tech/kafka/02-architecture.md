# 아키텍처 — Broker, Topic, Partition, Offset

## 개념

### 전체 구조

```
                         Kafka Cluster
                ┌──────────────────────────────────┐
[Producer] ───▶ │  Broker 1  Broker 2   Broker 3   │ ───▶ [Consumer Group A]
[Producer] ───▶ │  (P0 리더)  (P1 리더)   (P2 리더)   │ ───▶ [Consumer Group B]
                │  (P1 복제)  (P2 복제)   (P0 복제)   │
                └──────────────────────────────────┘
                     ▲ 메타데이터 관리: Controller (KRaft / ZooKeeper)
```

| 구성 요소 | 설명 |
|---|---|
| **Broker** | 카프카 서버 1대. 메시지를 저장하고 Producer/Consumer 요청을 처리 |
| **Cluster** | 여러 Broker의 묶음. 보통 3대 이상으로 구성 |
| **Topic** | 메시지의 논리적인 분류 (DB의 테이블과 비슷한 개념) |
| **Partition** | 토픽을 물리적으로 나눈 단위. 실제 데이터가 저장되는 곳 |
| **Offset** | 파티션 안에서 각 메시지의 고유한 순번 (0부터 증가) |
| **Segment** | 파티션을 디스크에 저장하는 실제 파일 단위 |
| **Controller** | 브로커 상태, 파티션 리더 선출 등 클러스터 메타데이터를 관리하는 역할 |

### Topic과 Partition

```
Topic: order-created (파티션 3개)

Partition 0: [0][1][2][3][4][5]  ← 새 메시지는 끝에 추가
Partition 1: [0][1][2][3]
Partition 2: [0][1][2][3][4]
```

- 토픽은 **1개 이상의 파티션**으로 구성된다.
- 각 파티션은 **독립적인 append-only 로그**다. offset도 파티션마다 따로 매겨진다.
- 그래서 메시지를 가리키려면 `토픽 + 파티션 번호 + offset` 세 가지가 필요하다.
- 파티션들은 여러 브로커에 **분산 배치**된다 → 한 브로커에 부하가 몰리지 않는다.

### Offset

- 파티션 내에서 메시지 위치를 나타내는 번호. 한 번 정해지면 바뀌지 않는다.
- Consumer는 **"이 파티션에서 몇 번까지 읽었다"** 를 offset으로 기록(커밋)한다.
- 커밋된 offset은 카프카 내부 토픽 `__consumer_offsets`에 저장된다.

```
Partition 0: [0][1][2][3][4][5][6][7]
                         ▲           ▲
              committed offset    log end offset
              (여기까지 처리 완료)   (마지막으로 쓰인 위치)
              
              → 둘의 차이 = Consumer Lag (밀린 메시지 수)
```

> **Consumer Lag**는 컨슈머가 생산 속도를 따라가지 못하고 있는지 판단하는 핵심 모니터링 지표.

## 동작 원리

### 1. 메시지가 어느 파티션으로 가는가 (파티셔닝)

| 상황 | 파티션 결정 방식 |
|---|---|
| 파티션 번호를 직접 지정 | 그 파티션으로 |
| **key가 있음** | `hash(key) % 파티션 수` → **같은 key는 항상 같은 파티션** |
| key가 없음 | Sticky 파티셔너: 한 파티션에 배치를 채운 뒤 다음 파티션으로 (카프카 2.4+) |

**순서 보장은 파티션 안에서만** 된다. 그래서 순서가 중요한 데이터는 같은 key를 쓴다.

```
key = "user-123" 의 주문 생성 → 결제 → 배송  ── 모두 Partition 1로 → 순서 보장 ✅
key 없이 전송                                  ── 여러 파티션에 흩어짐 → 순서 보장 ❌
```

⚠️ 파티션 수를 늘리면 `hash(key) % 파티션 수` 결과가 바뀌어 **같은 key가 다른 파티션으로 갈 수 있다.** 그래서 파티션 수는 처음에 여유 있게 정하는 게 좋다. (파티션은 늘릴 수만 있고 줄일 수는 없다.)

### 2. 브로커는 어떻게 저장하는가 (Segment)

파티션은 디스크에 하나의 큰 파일이 아니라 **여러 개의 세그먼트 파일**로 나뉘어 저장된다.

```
/kafka-logs/order-created-0/        ← 토픽명-파티션번호
  ├── 00000000000000000000.log      ← 실제 메시지 (offset 0부터)
  ├── 00000000000000000000.index    ← offset → 파일 내 위치
  ├── 00000000000000000000.timeindex← timestamp → offset
  ├── 00000000000000052340.log      ← 다음 세그먼트 (offset 52340부터)
  └── ...
```

- 새 메시지는 항상 **마지막(active) 세그먼트**에만 추가된다.
- 세그먼트가 일정 크기(기본 1GB)나 시간에 도달하면 닫고 새 세그먼트를 만든다.
- 보관 기간이 지나면 **세그먼트 파일 단위로 통째로 삭제**한다 → 메시지 하나하나 지우는 것보다 훨씬 효율적.
- `.index` 파일 덕분에 특정 offset을 빠르게 찾을 수 있다.

#### 삭제 정책 (cleanup.policy)
- `delete` (기본): 보관 기간(`retention.ms`, 기본 7일)이나 크기 초과 시 오래된 세그먼트 삭제.
- `compact`: **같은 key의 최신 값만 남기고** 이전 값은 정리. "각 사용자의 최신 상태"처럼 상태 저장용 토픽에 사용.

### 3. 복제 (Replication) — 간단히

- 각 파티션은 여러 브로커에 복제된다 (`replication.factor`, 보통 3).
- 복제본 중 하나가 **리더(Leader)**, 나머지는 **팔로워(Follower)**.
- **읽기/쓰기는 리더가 처리**하고, 팔로워는 리더의 데이터를 따라 복제한다.
- 리더가 있는 브로커가 죽으면 팔로워 중 하나가 새 리더가 된다.

> 자세한 내용(ISR, acks 등)은 [05-replication.md](05-replication.md)에서 정리.

### 4. Consumer Group과 파티션 할당

- 같은 그룹의 컨슈머들은 **파티션을 나눠서** 읽는다.
- **하나의 파티션은 그룹 내 컨슈머 하나에만 할당**된다. (한 컨슈머는 여러 파티션을 맡을 수 있음)
- 다른 그룹은 같은 토픽을 **독립적으로 처음부터** 읽을 수 있다.

```
Topic (파티션 3개)

Group A (컨슈머 2개)          Group B (컨슈머 4개)
  C1 ← P0, P1                   C1 ← P0
  C2 ← P2                       C2 ← P1
                                C3 ← P2
                                C4 ← (놀고 있음) ❗
```

→ **컨슈머 수 > 파티션 수 이면 남는 컨슈머는 아무것도 안 한다.** 파티션 수가 곧 최대 병렬 처리 수.

> 리밸런싱, offset 커밋 방식은 [04-consumer.md](04-consumer.md)에서 정리.

### 5. Controller와 메타데이터 관리

- 클러스터에는 **Controller** 역할을 하는 노드가 있다.
- 역할: 브로커 생존 감시, 파티션 리더 선출, 토픽 생성/삭제 등 메타데이터 관리.
- 과거에는 **ZooKeeper**라는 외부 시스템이 이를 담당했지만, 카프카 3.x부터 **KRaft** 모드로 카프카 자체가 관리하고, 4.0부터는 ZooKeeper가 완전히 제거되었다.

> 자세한 내용은 [07-kraft.md](07-kraft.md)에서 정리.

## 장단점 / 비교

### 파티션 기반 구조의 장점
- **수평 확장**: 파티션을 여러 브로커에 나눠 저장하고, 컨슈머도 파티션 수만큼 병렬로 늘릴 수 있다.
- **부하 분산**: 파티션 리더가 여러 브로커에 흩어져 있어 읽기/쓰기 부하가 분산된다.
- **빠른 저장/삭제**: append-only + 세그먼트 단위 삭제로 디스크를 효율적으로 사용.
- **장애 대응**: 복제 + 리더 재선출로 브로커 하나가 죽어도 서비스가 계속된다.

### 단점 / 주의점
- **전체 순서 보장 불가**: 순서는 파티션 안에서만 보장된다.
- **파티션 수 결정이 어렵다**: 늘리면 key → 파티션 매핑이 바뀌고, 줄일 수는 없다.
- **파티션이 너무 많으면 비용 증가**: 파일 핸들, 메모리 사용이 늘고 리더 선출과 리밸런싱이 느려진다.
- **Hot Partition**: 특정 key에 트래픽이 몰리면 한 파티션(한 브로커)에 부하가 집중된다.

### 파티션 수 정하는 기준 (대략)
- `목표 처리량 ÷ 컨슈머 1개당 처리량` 이상
- 앞으로 늘어날 컨슈머 수를 고려해 **여유 있게**
- 너무 크게 잡지 않기 (브로커당 수천 개 이상은 부담)

### 개념 비교 — RDB에 비유하면

| Kafka | RDB 비유 | 차이점 |
|---|---|---|
| Topic | 테이블 | 수정/삭제 없이 추가만 가능 |
| Partition | 샤드 | 순서 보장의 단위 |
| Offset | 자동 증가 PK | 파티션마다 따로 증가 |
| Consumer offset | 읽은 위치 북마크 | 컨슈머 그룹마다 따로 관리 |
